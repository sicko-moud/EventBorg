# DECISIONS

- M1: Mejeriet and Cathrinesminde have no own event pages; listed as `type: none` (social-only) sources so story matching works; their events arrive via sonderborg.dk.
- M1: Dropped billet.msj.dk (robots.txt disallows all), sonderjyske.dk (robots disallows), kalender.sdu.dk (behind login), opdagdanmark.dk (third-party aggregator, prefer primary sources).
- M1: Churches, sports clubs and SDU student orgs have no public machine-readable calendars; covered via sonderborg.dk until M3 social inbox.
- M1: ig/fb handles taken only from each source's own website footer links, never guessed.
- M1: Per-source `every` interval + conditional GET; html_llm pages are re-sent to Gemini only when their main text hash changes.
- M1: html_llm sends one page per LLM call (a page holds many events); summaries/fallback categories are batched 15 per call.
- M1: Added `ad` (all-day / time unknown) key to the data model; `s` is then local midnight.
- M1: Online events are dropped (not inside the municipality).
- M1: JSON-LD price "0" is treated as unknown, not free (WordPress plugins emit it as a placeholder).
- M1: Municipality check order: Danish zip → lat/lng polygon → town/outside-town names → source `local` flag.
- M1: Title similarity also returns 1.0 when one title's words are a subset of the other's (≥2 shared words), e.g. "Artist" vs "Artist – Tour 2026".
- M1: URL-based dedupe ignores homepages and listing pages (they don't identify one event).
- M1: IDs stay stable: a new ID that dedupe-matches last run's event re-uses the old ID; same-title shows on one day get time-qualified IDs.
- M1: Data branch is only force-pushed when events/sources/LLM cache/seen IDs change, or every 3 h, to stay well under Pages build limits.
- M1: GEMINI_MODEL defaults to the `gemini-flash-lite-latest` alias (fast, rarely overloaded on the free tier); override via repo variable.
- M1: E-mail addresses and phone numbers are scrubbed from descriptions.
- M1: A date-only record joins at most one timed cluster in dedupe (it had merged a 17:30 and a 20:30 show); merged events keep the timed start.
- M1: normalize_title drops "// Venue" suffixes, (XX) country codes and UDSOLGT/AFLYST/ekstra noise words, and folds Danish letters.
- M1: Venue town/zip swapped in source data (town "6400", zip "Sønderborg") is corrected.
- M1: User-Agent contact is the repo URL (CONTACT_EMAIL optional); Ticketmaster shows status `disabled` without a key.
- M1: Per-call fallback: only a call lite fails on (5xx, timeout, 429, unusable/truncated JSON) is retried once on GEMINI_FALLBACK_MODEL (gemini-flash-latest); a model that returns 429 is skipped for the rest of the run.
- M1: All LLM calls share a LLM_MAX_SECONDS (480) wall-clock budget, so slow models can't push the job past its 14-min CI timeout.
- M1: thinkingLevel "low" + maxOutputTokens 32768 (the only thinking setting both models accept); extracted descriptions capped at 200 chars so a 70-event page fits one reply.
- M1: A source whose last fetch ended in llm_unavailable/llm_quota is due on every run until it succeeds, regardless of its `every` interval.
- M1: flash-lite sometimes stops after 1–15 events on a 70-event page (same input gave 72, 1, 15). An html_llm reply with fewer than ¼ as many events as the page has distinct [links] counts as a lite failure → flash-latest; if flash is down, lite gets a second try and the fuller reply wins.
- M1: html_llm stores its PROMPT_VERSION per source and re-extracts all pages once when it changes (x3 drops the truncated results cached under x2).
- M2: Push decisions are made in the run step (persisted on the data branch) and sent by a separate step after publish, so a failed publish can't cause duplicate pushes.
- M2: Quiet hours 22:00–08:00 Copenhagen: pushes queue in state meta.pushq and the first run after 08:00 sends them, grouped; a queue change forces a publish.
- M2: Silent backfill: a source with ≥10 new events in one run that are ≥50% of its listing counts as a first ingest (fixes truncated-extraction recovery, 37 pushes in one run).
- M2: Flood guard: more than 8 pushable events in one run → every category with ≥2 of them is grouped.
- M2: FCM conditions allow 5 topics: 'all', c_X and the first 3 source topics; followers of a 4th+ source of one event/group get no push (rare).
- M2: Event push data = compact event JSON without desc (≤3.8 KB, drops sum/tags if needed) so the app can insert it into its cache; group push = category, count, up to N {id,t,s,v.n}. Android priority HIGH, ttl 12 h, restricted to app.eventborg, collapse key c_<cat> for groups.
- M2: FCM OAuth JWT signed with `cryptography` (one CI-only dependency) instead of google-auth.
- M2: /extract takes JSON {text, img (base64), mime}; a link in the text is read only if robots.txt allows it, checked on every redirect hop; login walls (Instagram/Facebook) return blocked_url so the app can ask for a screenshot.
- M2: Extraction prompt + schema live in shared/extract.json (Worker now, M3 inbox job later); field names match html_llm's raw format.
- M2: /extract returns an HMAC-signed token of the draft + confidence; /submit keeps conf only if the token verifies (≤24 h) and flags edits to title/start/venue/town, so clients can't assign their own confidence.
- M2: A past start whose year doesn't appear in the shared text is rolled to the next occurrence (flash-lite returned 2025 for "lørdag d. 13. december"); the prompt also gets today's weekday.
- M2: Worker Gemini calls: primary → fallback → primary within a 45 s budget (both free models 503 often).
- M2: Rate limits use Workers rate-limit bindings (per IP: extract 6/min, submit 4/min; extract 30/min overall): no KV writes, nothing stored.
- M2: Dispatch throttle: KV lock (60 s TTL) + pending flag flushed by a 1-minute Worker cron (~1.4k KV reads/day; writes only per item).
- M2: App submissions store sender=null (no device id or IP) and never count as a trusted sender.
- M2: /privacy, /data-deletion, /organizers in EN/DA (?lang= or Accept-Language); / shows /organizers. The DELETE/SLET command and Meta's deletion callback are described now and built in M3.
- M2: Worker deployed to https://eventborg.eventborg-worker.workers.dev (workers.dev subdomain auto-registered); KV namespace id is in wrangler.toml (not a secret). GH_TOKEN not set yet, so /submit skips repository_dispatch and the 15-min cron picks items up.
- M2: `python -m pipeline push --test` (and workflow_dispatch input test_push) sends one event to the `test` topic only, to check FCM credentials without reaching subscribers.
- M2: google-services.json lives in android/app/ (the app module M4 will create); both Firebase files stay gitignored. The same service account is a GitHub secret (event pushes) and a Worker secret (M3 story alerts).
- M3: Meta docs (2026-11-21): Instagram DM/story-mention webhooks from people without a role on the app, and replies to them, need App Review (Advanced Access, instagram_manage_messages) plus Business Verification; Standard Access + Live is not enough. All Instagram code is built and works for app-role users now; public use waits on that review.
- M3: Facebook Page feed/mention webhooks carry data of people without an app role, so they would need App Review too: skipped per spec. Page (Messenger) DMs are not handled.
- M3: WhatsApp on our own number needs no App Review; the first 1,000 service replies per number per month are free (charged after, since Oct 2026), so the 900/month cap stays.
- M3: Social tokens stay in the Worker; the inbox job uses authenticated /job/* endpoints (pull, media stream, ack+reply, Business Discovery pass-through). GitHub holds only INBOX_TOKEN.
- M3: Replying needs the raw sender id, so it is kept AES-GCM-sealed (key derived from SIGNING_KEY) in the KV item, never leaves the Worker, and is refused after 23.5 h; privacy page says so.
- M3: Sender hash = HMAC(SIGNING_KEY, channel|id), 20 hex; it is also KV key metadata, so DELETE/SLET finds a sender's items with one list call.
- M3: Meta redeliveries are deduped by a hashed message id in the job's done list (also within one batch); no extra KV writes.
- M3: Acks (KV delete + reply) run as a step after publish, so a failed publish never loses items or sends "Added".
- M3: Inbox events persist in state/inbox.json and rejoin every run before dedupe; social/inbox sources rank last in merges so web data wins.
- M3: Corroboration = dedupe match with an event from another source or an inbox event from another sender; trust grows only for event ids we didn't have (resends don't count).
- M3: Past events and non-events are dropped silently; >120 days or unconfirmed location go to review and, if approved, appear once inside the horizon.
- M3: Issues carry the fields as YAML plus a key marker; edits made before `approve` are published, also for issues whose state record was lost. The workflow also runs on `issues: labeled` (approve only).
- M3: Business Discovery: ≤6 accounts per run, each every 90–120 min (spread by id hash), latest 8 posts ≤21 days old, captions batched 10 per call; X-App-Usage ≥80% or rate-limit codes pause polling; a source's first poll is silent. Posts of a listed source count as a trusted sender; img=null (CDN URLs expire, no re-hosting).
- M3: Meta documents no owner for a forwarded story, so it matches the message text against handles/names (then the sender's username); story_mention resolves the sender via the User Profile API, cached as hash→source id for 7 days.
- M3: /story-seen accepts a ts from the last 30 min; one report raises the alert (3 h cooldown bounds abuse; 2-report rule is an M7 idea).
- M3: Relative dates and missing years resolve against the post/message date (Python port of fixYear); the shared spec is split into intro / intro_batch / rules (d2) for single and batched calls.
- M3: Phone scrub now also removes a number followed by a sentence period ("Ring 12345678.").
- M3: Graph API version is a Worker var (v27.0, latest on 2026-11-21).
- M3 revision (owner, 2026-11-21): Telegram dropped completely: webhook, media, replies, /job/setup, TG_* secrets/vars, pages and spec. DELETE/SLET no longer takes a leading slash (that was for bot commands).
- M3 revision (owner): public Instagram DMs and story mentions sit behind Worker var IG_PUBLIC_INBOX="false" (code kept for a later App Review); Business Discovery polling and Meta's deletion callback stay on.
- M3 revision (owner): WhatsApp is live only when WA_TOKEN, WA_PHONE_ID and WA_NUMBER all exist; otherwise webhook messages are dropped and media/replies return "inactive", with no errors and no mention on the pages.
- M3 revision: GET /channels {ig, wa} (1 h cache) lets the app's "Add your event" screen show only live channels; the static pages use the same helper and hide DELETE steps and the trust rule when no message channel is live.
- M3 revision (owner): on-device notification detection becomes the primary story feature, plus a local-only watch list (IG/FB profiles, FB groups) and group-post alerts; specced for M5 in CLAUDE.md. The privacy page already describes it, so it is accurate when M5 ships.
- M5 spec: "Hide original notification" cancels only matched notifications; for a listed venue the user doesn't watch, only when EventBorg showed its own alert, so no notification disappears without a replacement.
- M5 spec: watching a listed source also subscribes st_<sourceId>, so other users' relayed sightings arrive too; profiles the user adds get no topic and never leave the phone.
- M5 spec: Facebook group notifications carry no post URL, so "Open" fires the original notification's tap intent while the app still holds it and otherwise opens the group page.
- M4: No local Android SDK (Android Studio installed but never set up), so the app builds in GitHub Actions (`android` workflow: assembleRelease, size check against the 6 MB target / 8 MB cap, APK artifact). Gradle wrapper 9.9.2 (jar checksum verified), AGP 9.5.2 with built-in Kotlin 2.4.21, compile/target SDK 37.
- M4: No Google Services plugin: app/build.gradle.kts reads the gitignored google-services.json into resValues; without it the app runs with push off (BuildConfig.FIREBASE). CI writes it from the GOOGLE_SERVICES_JSON secret.
- M4: Release builds are signed with the debug key unless EB_KEYSTORE (+ password/alias env vars) is set; a real keystore comes with the M6 README.
- M4: No ViewModels/Room/Retrofit: app-level Repo (StateFlow, OkHttp, ETag/If-None-Match, one JSON file each in noBackupFilesDir) and Prefs (DataStore) are shared by all screens; filtering ~300 events per recomposition is trivial.
- M4: Sections run chronologically: Today / Tomorrow / Later this week / This weekend / Next week / Later, plus "Ongoing" at the end for already-started events spanning more than 3 days (exhibitions), so they don't fill Today.
- M4: "Now"/"Tonight" skip those long events; "This weekend" runs Fri 17:00 – Sun 24:00; all-day events ending at 00:00 count that end day as included.
- M4: Event notification setting maps to topics (All → `all`; Favourites → `c_<cat>` + `s_<source>`; Off → none), story alerts to `st_all` / `st_<favourite source>`; subscriptions are diffed against a stored set and retried on the next change or app start. Defaults: All events, story alerts for favourites.
- M4: Search folds ø/oe→o, æ→ae, å/aa→a and strips accents on both sides; tokens are ANDed over title, venue, town, organizer, tags, description and the localized category name.
- M4: UI language EN/DA without AppCompat: LocaleManager on Android 13+ (plus locales_config for system settings), a small SharedPreferences value + attachBaseContext below.
- M4: Category art is an emoji on a per-category tint (no image assets); icons from material-icons-core plus three hand-added vectors (StarBorder, FilterList, OpenInNew).
- M4: Source page (tap a source): links, star, upcoming events. Social links open with ACTION_VIEW so the Instagram/Facebook app handles them; web links use a Custom Tab.
- M4: "Suggest a source" posts {name, url, note} to a new Worker endpoint POST /suggest (per-IP submit limit), queued in KV like drafts; the inbox job opens a public issue labelled `source` with the values in a code block (markdown and @mentions inert, phones/e-mails scrubbed). The app and the privacy page say it is public.
- M4: Event cache lives in noBackupFilesDir (not backed up); DataStore prefs (saved, favourites, settings) are included in Android backup.
- M4: FCM's own manifest adds WAKE_LOCK for message delivery; EventBorg's code holds none.
- M4: An offline fetch is retried after 3, 10 and 30 s while the app is on screen (found by the emulator test: Wi-Fi came up seconds after launch); Retry/pull replaces a waiting retry; nothing runs in the background.
- M4: Emulator smoke test (CI, opt-in via `[smoke]` in the commit message or workflow_dispatch): API 35 emulator, cold start time, screenshots of every main screen in EN and DA, fails on FATAL EXCEPTION.
- M4: Danish feed tab is "Forside" ("Arrangementer" wrapped in the nav bar).
- Students: IDA events via a new `sitemap` adapter (IDA's public meetup sitemap + per-page schema.org JSON-LD; the group pages load events from a private API, so not used). Every page is fetched once, only events located in the municipality are kept, other pages are remembered for 30 days; the first fill is spread over runs (120 pages/run) and stays push-silent until done.
- Students: `audience: students` on a source tags all its events `students`; text/category rules add the tag too (studerende, students, SDU, fredagsbar, IDA "studieevents" organisers). The category stays what the event is (sports, nightlife…); the tag drives priority.
- Students: the app ranks student events first by default (setting "Student events first"): a "For students" row of the next 14 days above the feed, the Students quick chip first, a 🎓 mark on cards, and a "Student events only" filter. The feed sections stay chronological. Youth-tagged events (sonderborg.dk "Unge 15-30 år", which the municipality presents "for young people and students") count as student events too; without them the row is empty most weeks.
- Students: ten SDU Sønderborg student associations added as social-only sources (ig/fb from SDU's official association list) for story alerts, watch-list suggestions and Instagram post polling. gearsdu.com (G.E.A.R.) is not listed: the domain now serves a gambling-app page; mejeriet.dk is an unrelated firm.
- Categorizer: "Unge 15-30 år" no longer maps to nightlife (it is an age group, the youth tag covers it), and sport is matched before theatre so sonderborg.dk's "Sport, dans og vandringer" is sports.
